# Open decisions

**Status:** completed historical Phase 0–11 decision register. The current
[Platform Architecture](platform-architecture.md) and
[RRP 1.0.0 Implementation Plan](platform-implementation-plan.md) own forward
direction; progressive planning for the current stage will establish any active
decision register required for that stage's implementation.

## Purpose

This list records maintainer decisions that affect product or architecture.
They should be resolved when the named phase needs them. They do not block
earlier work unless stated.

| Decision | Why it matters | Needed by | Current direction |
|---|---|---:|---|
| Open-source license and content/asset licensing | Determines permission to distribute and reuse source/assets | Resolved in Iteration 11.6 | Apache-2.0 installed after the bounded dependency/asset review found no concrete incompatibility; dependency licenses remain their own and publication remains separate |
| Initial schema/specification format | Affects readable and machine-validated contracts | Resolved in Phase 1 | YAML is the human-authored source; executable R validation uses the independently locked `yaml` dependency |
| Pre-1.0 compatibility policy | Determines when draft interfaces may change and how migrations are stated | Resolved in Phase 1 | Patch changes are narrowly compatible; semantic or requiredness changes increment the minor line and require explicit consumer support |
| Generic canonical bundle, registration, and dependency model | Prevents representation and status mechanics from being invented by individual domains | Resolved in Phase 2.1 | One bundle instance registers independently versioned domains/capabilities with required, conditional, or optional classes and simple acyclic typed dependencies |
| First canonical clinical-domain capability profile | Determines actual required, conditional, optional, and unavailable clinical inputs | Resolved in Phase 2.2 | Required discharge episode plus optional baseline risk and optional episode event; available optional domains may have zero rows, while unavailable/unsupported domains have no instance |
| Initial canonical controlled vocabularies | Prevents local baseline/event values from silently changing portable meaning | Resolved in Phase 2.2 | Three exclusive baseline value types and six bounded event types; new platform values require a new minor line and mapping/conformance evidence |
| Canonical additional-field and extension policy | Determines portability versus local flexibility at the public handoff | Resolved in Phase 2.2 | Initial clinical records reject unknown fields; source-specific columns remain implementation-owned and a formal extension mechanism is deferred until justified |
| Canonical occurrence/availability declarations | Establishes future-information conformance without forcing universal field names | Resolved in Phase 2.1 | Each domain identifies its occurrence/effective and availability/recorded roles and may prohibit availability before occurrence |
| Partial synthetic/local composition | Affects progressive source replacement and cross-domain coherence | Resolved for Phase 3; revisit with a concrete mixed implementation | The reference is one complete source implementation; silent cross-implementation composition is unsupported |
| Synthetic implementation identity and scale | Makes source schema, generator, mapping, implementation, and runs independently attributable | Resolved in Phase 3 | Separate versioned identities; declared seed/as-of/scale configuration; test scale has 4 patients/6 episodes and reference scale has 24/36 |
| Distribution of prebuilt synthetic inputs/products | Affects time-to-first-use and repository size | Resolved for Phase 6 | Do not commit generated source, canonical, history, or product bundles; authoritative human operations rebuild them under ignored paths |
| First default estimand(s) | Own horizon, event, terminal, output, and coherence semantics | Resolved in Iteration 4.1 | `platform.readmission-next-day-conditional-hazard@0.1.0`: first readmission in `(t, min(t + 1 day, W)]`, conditional alive/readmission-free/eligible at `t`; death competes, probability is bounded, and daily hazards need not be monotone |
| Planned versus unplanned readmission | Affects canonical event meaning and any narrower readmission estimand | Future canonical/estimand iteration | The initial canonical profile has no plannedness field; estimand `0.1.0` therefore uses first canonical readmission and makes no unplanned-readmission claim |
| Provider trust and registration boundary | Controls arbitrary code execution and local extensions | Resolved in Iteration 4.2 | Trusted code explicitly pairs a conforming declaration and callable in a process-local registry; ordinary configuration selects an exact registered ID/version and cannot load paths, code, packages, or remote plugins |
| First provider runtime | Affects package/API scope | Resolved in Iteration 4.2; extended in 5.1 | `rrpruntime@0.3.0` preserves provider behavior and adds history ports; execution-result `0.2.0` adds run/attempt/retry lineage; the shipped transparent provider remains nonclinical conformance software |
| Provider and trained-model identity | Prevents executable method, fitted artifact, and canonical source models from being conflated | Resolved for Phase 4 | Provider identity is always explicit; a separate model/artifact reference is optional and explicitly null for the fixed transparent formula |
| Estimate identity and execution failure representation | Determines safe downstream history semantics | Resolved for Phase 4; persistence semantics Phase 5 | Estimate comparison identity includes run, execution, request, state, estimand, provider/model, and interval; unsupported/failure/invalid output are execution results with no fabricated estimate |
| Reference local persistence technology | Realizes ports and the first durable slice | Resolved in Iteration 5.2 | `reference.duckdb-persistence@0.1.0`; single-file ACID reference with one controlled writer, explicit close/reopen and checkpointed backup; not a production mandate or platform dependency |
| Idempotency, correction, invalidation, and restatement semantics | Determines operational truth | Resolved for the initial history boundary in Iteration 5.1; migration/retention maturity Phase 6 | Identical identity/content is a no-op; conflicts fail; invalidations are append-only overlays; restatements are new attributed runs; raw facts remain retained |
| Default logical product suite | Determines supplied app and compatibility surface | Resolved in Iteration 6.1 | Required core `platform.initial-risk-product-set@0.1.0`: current episode/estimand risk, persisted accepted-estimate history, and valid terminal run summary; no decision-oriented products |
| Retained decision and lineage records | Determines what has independent historical meaning | Phase 6 | Persist only records that need operational/governance attribution |
| Product materialization versus query | Affects product adapters and freshness semantics | Resolved for the Phase 6 reference | `reference.yaml-product-bundle@0.1.0`; immutable complete YAML sets plus atomic `CURRENT.yml`, MD5 accidental-corruption evidence, whole-set access validation, factual freshness with no universal stale threshold; bundles remain uncommitted |
| Initial application access and dependency | Keeps UI replaceable and upstream-independent | Resolved for the Phase 6 reference | Inject validated `list/read/metadata` product access; direct dependency is Shiny only; valid zero rows render empty states and access failure is safe/actionable |
| Stable public operation surface and classification | Establishes human initialization, preflight, producer conformance, run, history, product, and app intent without hidden orchestration | Resolved in Iteration 7.1; producer validation added in 10.1 | Public operations cover initialize, doctor, two validation modes, configured-producer validation, one run, inspect, materialize, app validate/launch, and artifact/target build/validation; lower-level proof operations remain advanced/development |
| Initialization and doctor semantics | Makes fresh installation and recovery explicit | Resolved in Iteration 7.1 | Dependency restore remains explicit; initialization creates only the ignored writable local root; doctor is read-only, warning-tolerant for absent history/products, and fails incompatible state |
| Operations registry and convenience workflow | Controls drift without creating a command framework | Resolved in Iteration 7.1 | Small YAML metadata registry is justified; no all-in-one wrapper or CLI router is added because distinct public commands are already clear |
| Scheduling responsibility and adoption sequence | Separates platform behavior from operator cadence and replacement order | Resolved in Iteration 7.1 | Platform owns what a run does; operator/external automation owns when. Progressive component replacement is supported without a mandatory order |
| Role of `readmit` and a CLI | Determines optional control surfaces | Resolved for Phase 7; revisit only with concrete demand | No CLI framework is justified; optional future clients must invoke the same tested operations |
| Target-neutral reduced application artifact | Prevents the first host from defining platform packaging | Resolved in Iteration 8.1 | `platform.reduced-application-artifact@0.1.0`; closed 27-file product-only unit, direct R/Shiny/YAML dependency declaration, deterministic instance/build identities, immutable builds plus atomic current pointer, standalone validation |
| Connect deployment ownership and publication destination | Governs safe replacement, markers, commit, and push | Resolved in Iteration 8.2 | Generate a disposable local Git repository at an explicit outside-platform destination; replace only untouched owned output; stage without commit/remote; operator owns commit, remote, push, and Connect deployment |
| Observability event schema, default verbosity, routing, and retention | Affects privacy and operations | Resolved for the Phase 9 local foundation; deployment routing/retention remain target-owned | `platform.operation-run-context@0.1.0` plus `platform.operational-diagnostic-event@0.1.0`; base-R in-memory emitter, callable sink, normal console default, quiet/debug renderer modes, strict shallow safe context, no retained default, and deployment-owned future routing/retention |
| Canonical producer trust, selection, and adopter handoff | Defines how one installed health-system implementation supplies canonical data without executable configuration | Resolved and independently proven in Phase 10 | `platform.canonical-producer@0.1.0`; trusted process-local callable registration; exact single installation selection; generic result/admission/conformance; a materially different test-owned producer proves unchanged downstream substitution while the default remains the shipped reference |
| First public platform release identity, unit, and acquisition | Defines what is versioned and how adopters obtain an authoritative release | Resolved and published in Iteration 11.7 | Platform `v0.1.0` is the validated whole-repository source tree at `7a3cca6`; GitHub is source/release authority with an immutable annotated tag, GitHub Release, attached exact candidate archive/checksum, and published-state acquisition proof |
| Hospital implementation distribution and extension packaging | Determines how adopter code composes without routinely editing/forking the platform | Resolved and published in Iteration 11.7 | The independently versioned public `centralstatz/readmission-risk-pool-hospital-implementation` `v0.1.0` release contains one exact Platform archive, thin wrappers, one top-level environment, and fixed trusted composition. The GitHub repository remains generated output rather than CentralStatz source authority. Recipient changes remain outside that release architecture |
| CentralStatz branding and stewardship policy | Affects public docs and assets without gating core operation | Resolved in Iteration 11.2 | CentralStatz Statistical & Data Sciences LLC is project steward/release publisher; Alex Zajichek is initial maintainer. Use factual stewardship language and keep optional services separate from open-source rights |
| Supported R/OS matrix and release cadence | Defines support commitment and release validation | Resolved narrowly in Iteration 11.6 | Ship the platform lock and use `renv::restore()`; support R 4.4.x and claim only the recorded macOS test environment plus separately successful CI environments. Broader OS/R claims require new evidence |
| Contribution, support, security, and disclosure policies | Required for governed public collaboration | Resolved and installed in Iteration 11.6 | Lightweight contribution guidance with DCO and no CLA/assignment; best-effort support with no SLA; GitHub issues; private vulnerability reporting where available; operator-owned deployment/PHI security; optional CentralStatz services remain separate |

## Decision-record expectation

When a decision becomes material, record its context, chosen option,
alternatives, consequences, and affected contracts or phases in the
[implementation record](platform-implementation-record.md) or a linked decision
record. Update this list rather than leaving a resolved question open.
