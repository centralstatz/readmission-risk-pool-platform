# Connect Cloud Git realization

## Purpose and status

Iteration 8.2 implements `platform.connect-cloud-git-realization@0.1.0`, the
first target-specific consumer of the reduced application artifact. It proves
that the same closed product-only runtime can become a complete local Git
repository for Posit Connect Cloud without making Connect part of the platform
core.

```text
authoritative platform
        ↓
validated platform.reduced-application-artifact@0.1.0
        ↓
platform.connect-cloud-git-realization@0.1.0
        ↓
standalone local Git repository
        ↓
STOP: operator-controlled publication and deployment
```

The realization is fictional/nonclinical reference deployment software. It
does not establish production, security, compliance, privacy, availability, or
clinical fitness.

## Verified target requirements

The target design was checked on 2026-08-13 against maintained Posit Connect
Cloud documentation:

- [R platform support](https://docs.posit.co/connect-cloud/user/platform/r.html)
  says R content requires `manifest.json`; Connect Cloud uses it to choose R
  and install packages and does not currently use `renv` for environment setup.
- [Deploy a Shiny app](https://docs.posit.co/connect-cloud/how-to/r/shiny-r.html)
  documents a Git repository with root `app.R` and a manifest generated by
  `rsconnect::writeManifest()`.
- [Create new content](https://docs.posit.co/connect-cloud/user/publish/01-new.html)
  makes repository, branch, and primary-file selection an external Connect
  operation.

Those are target requirements. Keeping the complete artifact unchanged under
`artifact/`, retaining a pruned generator lock, using branch `main`, and
staging generated files without a commit are reference-realization choices.
The closed artifact inventory, application/product compatibility, and direct
R/Shiny/YAML roots are inherited from Iteration 8.1.

## Contract and generated repository

The contract is
[`platform.connect-cloud-git-realization@0.1.0`](../../contracts/deployment/connect-cloud-realization.yml).
One realization has 37 staged regular files plus `.git/`:

```text
chosen-destination/
├── app.R
├── manifest.json
├── manifest.md5
├── renv.lock
├── CONNECT-REALIZATION.yml
├── CONNECT-REALIZATION.md5
├── validate-connect-cloud.R
├── README.md
├── R/connect-cloud-validation.R
├── contracts/connect-cloud-realization.yml
└── artifact/                 # unchanged 27-file reduced artifact
```

The root `app.R` is a target adapter that loads and constructs the embedded
artifact app. It does not reach into the platform repository. The artifact is
nested rather than modified because its manifest is a closed inventory and it
must remain usable by future peer realizations. A later OCI/container target
can consume the same artifact without depending on this layout or contract.

## Identity and dependency realization

The realization ID covers the target specification, source artifact identity,
target-owned files, and dependency closure. It excludes destination path,
folder name, generation time, Git commit, remote, publication, and Connect
content identity. `CONNECT-REALIZATION.yml` keeps those concepts distinct and
records provenance and non-claims.

The artifact's exact direct roots remain `shiny@1.10.0` and `yaml@2.3.10`.
The builder prunes the platform lock transitively from only those roots and
uses build-only `rsconnect@1.3.1` to produce target-required `manifest.json`.
The pruned `renv.lock` is retained as auditable generator input; Connect Cloud
consumes the manifest, not the lock. Platform-only DBI, DuckDB, runtime,
provider, persistence, source, product-writer, test, and operation dependencies
are excluded.

## Git and destination semantics

The generated repository is initialized on `main`; all 37 generated files are
staged. It has no commit, remote, or repository-local author identity. This is
the natural boundary before publication and avoids inventing or mutating the
operator's Git identity. The operator reviews and commits using their identity.

The destination is explicit and is not part of identity. It must be outside
the authoritative repository and have an existing regular parent directory.
Generation stages and fully validates a candidate before destination mutation.

- A nonexistent destination is created by promotion of the staged repository.
- An identical owned destination is an idempotent no-op.
- A changed artifact or realization replaces only an independently valid,
  remote-free, uncommitted, unmodified generated destination.
- An unrelated, committed, remotely configured, corrupt, or locally modified
  destination is refused without overwrite.
- A failed source or staged validation leaves the destination untouched and
  removes staging state. Promotion failure attempts to restore the prior owned
  destination.

Generated repositories are disposable outputs, not customization branches or
second sources of truth. Supported future customization must enter through an
authoritative platform interface.

## Independent validation and publication boundary

The generated validator uses only repository content and the installed package
library. It checks the exact manifest-backed inventory, safe paths, no
symlinks, checksums, contract and realization identity, unchanged source
artifact validity, artifact/application compatibility, manifest and lock
dependency closure, product coherence, root app construction, forbidden
platform machinery and secret patterns, and required Git state. Validation is
also exercised from a copied repository.

No platform operation creates a remote, commits, configures credentials,
pushes, calls Connect APIs, or deploys content. Publication and deployment are
external operator responsibilities. Real hospital deployment additionally
requires adopter-owned privacy, security, access-control, networking,
retention, and governance decisions.
