# Local reference platform operator manual

## Purpose and current support

This is the authoritative, human-first procedure for operating the complete
local fictional reference platform. It needs no AI and assumes only a local
installation of the repository's current files. A Git clone is today's
development acquisition path, not a permanent distribution contract.

The supported journey is:

```text
restore dependencies → initialize → doctor → run platform → inspect history
                     → materialize products → validate app
                     → build artifact → validate artifact
                     → generate/validate local Connect repository
```

The platform defines what each deterministic operation does. The operator
decides when to invoke it. Local operation, target-neutral artifact
construction, and the Connect Cloud local Git realization are supported;
remote publication, service deployment, scheduling, release, upgrade, and
production operation are not.
All data generated by this guide are deterministic, fictional, nonclinical,
and unsuitable for patient care.

Selected commands emit a correlated structured console lifecycle in addition
to their established human result. See
[Operational Diagnostics](observability-and-diagnostics.md) for privacy,
interpretation, and recovery rules. Events create no retained log and never
replace command exit status, operational history, validation, provenance,
metrics, or audit. Terminal failures expose a stable safe code and recovery
hint; no external logging integration is currently supplied.

## Installation prerequisites

Use R 4.1.0 or newer. From the installation root, restore the exact project
environment explicitly:

```sh
Rscript -e 'renv::restore()'
```

Dependency restoration is deliberately not hidden inside initialization. It
can download/install packages and has its own recovery behavior. The current
direct dependencies are `yaml`, adapter-owned `DBI` and `duckdb`, and app-owned
`shiny`; `rrpruntime` remains base-R-only and is installed temporarily by
operations.

## Initialize local state

Run:

```sh
Rscript operations/initialize-platform.R
```

This checks required installation files and packages, creates the ignored
local `build/` directory if absent, and verifies that it is a regular writable
directory. It writes no source-controlled file, initializes no database,
creates no history or products, performs no run, and launches nothing. It is
safe to repeat. To use another local root:

```sh
Rscript operations/initialize-platform.R --build-root build/local-reference
```

Success reports `platform.initialize-local`, `succeeded`, the local root, and
that neither history nor products were created. On failure, restore missing
dependencies/files or select a regular writable path; initialization never
repairs or deletes state.

Agent convenience: ask the repository agent to “initialize the local
platform”; it should invoke this exact operation.

## Run doctor

Run the read-only preflight:

```sh
Rscript operations/doctor.R
```

Doctor checks supported R, the locked `renv`/`yaml`/`DBI`/`duckdb`/`shiny`
dependencies, required repository/configuration/contract files, temporary
`rrpruntime` installation/loading, output-parent writability, DuckDB
compatibility and lifecycle, current YAML product integrity/compatibility/
coherence, and app readiness. It removes its temporary package library and
write probes. It never initializes, fixes, migrates, rebuilds, or runs the
platform.

Doctor does not require or judge Git cleanliness. Distribution is unresolved,
and a valid installation need not have Git at all. Repository milestone checks
and generated-state policy remain the validation operation's responsibility;
doctor checks only operator readiness and selected local lifecycle state.

Use explicit state locations when required:

```sh
Rscript operations/doctor.R --database build/my-fictional-history.duckdb --products build/my-reference-products
```

Severity has operational meaning:

- `pass` means that check is ready;
- `warning` is nonfatal expected or review-worthy state; and
- `failure` blocks the supported workflow and exits nonzero.

A fresh installation is healthy with warnings:

```text
Reference environment: ready
Operational history: absent
Latest valid run: none
Current product bundle: absent
Product source as-of: none
App: blocked_expected
```

That lifecycle becomes `history: available`, `bundle: valid`, and `app: ready`
after a successful run and materialization. Do not ship or manufacture prior
history merely to remove fresh-install warnings. Each warning/failure reports
an exact next or recovery action. Incompatible history is preserved for
compatible code or backup recovery; corrupt products are rebuilt from history,
never edited in place.

Agent convenience: “run doctor” maps exactly to
`Rscript operations/doctor.R`.

## Run one operational cycle

The authoritative operator-facing reference run is:

```sh
Rscript operations/run-platform.R --profile reference --scale test
```

It composes synthetic source generation/read, source validation, canonical
mapping/admission, eligibility/state, estimand requests, exact reference
provider execution, accepted estimates, and an atomic DuckDB terminal batch.
It does not build products, launch the app, schedule another run, deploy, or
publish. Default output is `build/reference-operational-history.duckdb`.

The deterministic default is safe to repeat: the same semantic identity and
content are an idempotent no-op; a conflict fails loudly. An intentional new
observation must have its own run identity and as-of context, for example:

```sh
Rscript operations/run-platform.R --profile reference --scale test --run-id runtime_reference_manual_20260802T120000Z --as-of 2026-08-02T12:00:00Z
```

Both `--run-id` and `--as-of` should be supplied deliberately for a new run;
when only `--as-of` is supplied, the reference operation derives a transparent
run ID. `--database PATH` selects another local store. Success reports the
operation/status, run ID, terminal status, family counts, and database path.

Agent convenience: “run the reference platform once” maps to the exact default
command above. An agent must report the human operation it invoked.

## Inspect operational history

Inspect the deterministic test run through the logical persistence port:

```sh
Rscript operations/inspect-reference-history.R --scale test
```

For an explicitly identified run:

```sh
Rscript operations/inspect-reference-history.R --database build/reference-operational-history.duckdb --run-id runtime_reference_manual_20260802T120000Z --view valid
```

Use `--view raw` only when invalidated facts must remain visible. Inspection is
read-only and reports lifecycle/family counts without exposing a mutable DBI
connection. Missing or incompatible history is not initialized automatically.

## Materialize products

Build, conform, stage, validate, and atomically publish products from retained
test history:

```sh
Rscript operations/build-reference-products.R --scale test --materialize
```

For a new or multi-run history scope, name every intended source run:

```sh
Rscript operations/build-reference-products.R --database build/reference-operational-history.duckdb --run-id runtime_synthetic_history_test_001 --run-id runtime_reference_manual_20260802T120000Z --materialize --products build/reference-products
```

This is a product refresh, not a platform run. It reads valid retained history,
never invokes a provider, and creates no estimate. It may run immediately,
later, or repeatedly against the same scope. Publication atomically replaces
only the current product pointer and retains prior immutable bundles.

Agent convenience: “materialize the reference products” maps to the first
command. “Refresh products” never implies a new estimation run.

## Validate and launch the app

Validate current product access and construct the Shiny app without a server:

```sh
Rscript operations/launch-reference-app.R --validate-only
```

Then launch the already validated current bundle:

```sh
Rscript operations/launch-reference-app.R
```

App validation and launch are read-only. They do not open DuckDB, run a source,
invoke runtime/provider code, rebuild products, or create history. Repeated
launches display the same current materialization. Use `--products PATH`,
`--host HOST`, and `--port PORT` when needed; stop the foreground server with
Ctrl-C.

Agent convenience: “validate the reference app” and “launch the reference app”
map to the distinct commands above. “Refresh the local reference app” is
ambiguous and unsupported shorthand: ask whether the intent is a platform run,
product refresh, or app reload.

## Three distinct refreshes

| Intent | Effect | Creates estimates/history? |
|---|---|---:|
| Platform run | Re-evaluates source/state/estimand/provider and appends a run | Yes |
| Product refresh | Reprojects selected retained history into products | No |
| App launch/reload | Displays the current valid materialized products | No |

The app never makes upstream data current. Materialization never estimates
risk. A platform run never silently changes what the app displays.

## Build and validate the reduced application artifact

After product materialization and app validation, build the target-neutral
runtime unit:

```sh
Rscript operations/build-application-artifact.R
Rscript operations/validate-application-artifact.R
```

The first command stages only the closed product-only allowlist, embeds the
current coherent product set, validates it, promotes an immutable local build,
and atomically updates the artifact-store pointer. The second runs the
artifact's own validator in an isolated vanilla R process and constructs the
Shiny app without monorepo runtime source. Neither command opens history,
rebuilds products, deploys, publishes, or requires credentials. Full inputs,
outputs, repeat behavior, and recovery are in
[Application Artifacts](application-artifacts.md).

Agent convenience: “build the application artifact” and “validate the
application artifact” map to those exact commands. Neither phrase authorizes a
target realization or external publication.

## Generate and validate the Connect Cloud repository

Choose an explicit destination outside the platform repository whose parent
already exists, then run:

```sh
Rscript operations/build-connect-cloud-deployment.R --destination PATH
Rscript operations/validate-connect-cloud-deployment.R --destination PATH
```

The generated repository contains the unchanged artifact plus the minimal
Connect adapter, declaration, dependency manifest, provenance, and validator.
It is initialized on `main`; all generated files are staged, with no commit,
remote, credential, or invented Git identity. Publication and Connect setup
remain operator-controlled external steps. Destination ownership,
regeneration, failure, and recovery behavior are in
[Connect Cloud Deployment Repository](connect-cloud-deployment.md).

Agent convenience: “generate a Connect Cloud deployment repository” and
“validate a Connect Cloud deployment repository” map to the exact commands
above. Neither authorizes commit, remote creation/configuration, push, or
deployment.

## Repeat, cadence, and estimand horizon

Execution cadence is operator-controlled. The current estimand's next bounded
one-day interval is methodological and estimand-controlled. They are not the
same concept: one-day quantity semantics do not impose a daily schedule.

- A new run/as-of identity appends one actual operational observation.
- An identical semantic retry is idempotent; conflicting content fails.
- Multiple runs per day are valid. Each retains its as-of time and target
  interval; products and the app keep every valid point without daily collapse.
- Overlapping target intervals are valid and independently identified.
- If an intended run is missed, no estimate exists for that time. There is no
  automatic backfill, future facts are not used to manufacture history, and the
  next run proceeds at its own as-of time.
- Products and the app show the history that exists; freshness shows the most
  recent successful represented run.

Scheduling and automation are external. Operators may use cron, Windows Task
Scheduler, Posit Connect scheduling, Airflow, enterprise orchestration, or
another approved tool to invoke these exact commands. None is required or
implemented here.

> The platform owns what a run does; the operator owns when runs occur.

## Operation inventory and classification

The lightweight [operation registry](../../operations/operations.yml) records
IDs, exact commands, purpose, mutation level, documentation, and classification.
It is drift metadata, not executable orchestration or business logic.

Public onboarding operations are initialize, doctor, development/checkpoint
validation, one platform run, history inspection, product materialization,
app validation/launch, artifact build/validation, and Connect repository
generation/validation. Advanced/debug operations preserve individual stages:

```sh
Rscript operations/generate-reference.R --scale test
Rscript operations/run-reference-runtime.R --input synthetic --scale test
Rscript operations/run-reference-estimation.R --input synthetic --scale test
Rscript operations/run-reference-history.R --scale test
Rscript operations/build-reference-products.R --scale test
Rscript operations/backup-reference-history.R --database build/reference-operational-history.duckdb --backup build/backups/reference-operational-history-001.duckdb
```

Documentation-only and phase-specific test entry points are development
operations. Lower-level operations remain supported for debugging, but normal
onboarding does not require Phase 1–6 internals. Every operation documents its
inputs, outputs, side effects, repeat behavior, failures, and recovery in this
manual or the linked focused guide.

No all-in-one workflow wrapper is supplied. The distinct state mutations are
important, and the short public commands already provide a clear manual
journey. A future wrapper must only invoke these operations and may not add
hidden logic or launch a long-running app implicitly.

## Troubleshooting

- **Dependency unavailable:** run `Rscript -e 'renv::restore()'`, then doctor.
- **Fresh state warnings:** run the next operation; do not treat absence as
  corruption.
- **DuckDB incompatible/locked:** preserve it, stop the writer, and use
  compatible code or a validated backup. Never destructively reinitialize.
- **Run identity conflict:** investigate changed meaning. Use a new identity
  only for a genuinely new computation.
- **Product bundle corrupt/incompatible:** preserve history and rebuild the
  complete bundle. Never repair checksums or members manually.
- **App blocked:** run doctor, then materialize products and validate-only.
- **Missed run:** resume with a new current as-of; do not fake a historical
  point.
- **Need a backup:** follow [Durable Reference History](reference-history.md).
- **Repository milestone failure:** follow [Validation](validation.md); do not
  substitute doctor for checkpoint validation.

## Deployment status

Local end-to-end operation, the target-neutral reduced artifact, and the
Connect Cloud local Git realization are supported. Connect is not the
definition of deployment. The platform uses build-only `rsconnect` to generate
the required local manifest, but no container target, remote/companion
repository mutation, publisher, credential, commit, push, Connect API call, or
external deployment command exists.
